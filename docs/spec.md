# مواصفات منصة إدارة مشاريع الاتصال المؤسسي — شركة ناف القانونية

> **الاسم الرمزي للمستودع:** `naf-comms`
> **الجمهور:** Claude Code (منفّذ البناء) + فريق ناف
> **الحالة:** مسودة معتمَدة للتنفيذ — الإصدار 1.0 — نوفمبر 2026
> **اللغة:** الواجهة عربية بالكامل (RTL)، والكود والتعليقات بالإنجليزية

---

## 0. تعليمات لـ Claude Code قبل البدء

1. **اقرأ هذا الملف كاملاً** قبل كتابة أي كود، ثم أنشئ `CLAUDE.md` في جذر المستودع يلخّص القرارات المعمارية والأوامر.
2. **واجهة Basecamp مُتحقَّق منها مسبقاً في الملحق (أ)** من الوثائق الرسمية (نوفمبر 2026) — اعتمد عليه مباشرة. ولا تخمّن في واجهات Google أو Univer؛ تحقّق منها من الوثائق الرسمية:
   - Basecamp API (مرجع إضافي فقط): `https://github.com/basecamp/bc-api` و SDK الرسمي `https://github.com/basecamp/basecamp-sdk`.
   - Google Sheets API v4: `spreadsheets.get` مع `includeGridData`.
   - Univer: `https://docs.univer.ai` — والتزم بالمكوّنات مفتوحة المصدر (`@univerjs/*`) فقط ما لم يُعتمد ترخيص Pro (انظر §5.3).
3. **إذا تعارض شيء في الوثائق مع هذا الملف، أو لم تتأكد من سلوك ما، توقّف واسأل** بدل الافتراض.
4. **لا تحذف ملفات ولا بيانات** (محلياً أو في Basecamp أو Drive) بدون تأكيد صريح من المستخدم.
5. نفّذ **حسب المراحل في §15** بالترتيب، ولا تنتقل لمرحلة قبل اجتياز معايير قبول سابقتها.
6. اكتب اختبارات لكل منطق مزامنة ومحوّل استيراد (الأجزاء الأخطر في المشروع).

## 1. الهدف

منصة ويب داخلية لناف لإدارة مشاريع الاتصال المؤسسي بواجهة **جداول مطابقة لتجربة Google Sheets**، حيث:

- كل **ملف (Workbook)** = **مشروع في Basecamp 5**.
- كل **ورقة (Sheet)** = **قائمة مهام (To-do list)** داخل ذلك المشروع.
- كل **صف رئيسي** = **مهمة (To-do)**، وكل **صف فرعي** = **مهمة فرعية (Subtask)** داخلها.
- **مزامنة ثنائية الاتجاه** لحظية: أي تعديل في المنصة يصل Basecamp، وأي تعديل في Basecamp يرجع للمنصة.
- **إنشاء ملف جديد** أو **استيراد ملف Google Sheets** كما هو (أوراقه، تنسيقاته، معادلاته، تنسيقه الشرطي، فلاتره).
- **تسجيل دخول موحّد** عبر نظام ناف `naf-id`، وهوية بصرية من سجل `naf-ui`.

### خارج النطاق (الإصدار الأول)
- تطبيق جوال أصلي (الواجهة متجاوبة فقط).
- مزامنة مع Google Sheets بعد الاستيراد (الاستيراد لمرة واحدة؛ الملف الأصلي لا يُمس).
- بطاقات Card Table وجداول Schedule في Basecamp.
- تشغيل Apps Script.

## 3. المستخدمون والصلاحيات

- **المصادقة:** عبر `naf-id` (نظام SSO الموحّد لمنصات ناف). افترض OIDC/OAuth2 مع JWT؛ **تحقّق من تفاصيل `naf-id` الفعلية من مستودعه أو اسأل قبل التنفيذ.**
- **الأدوار على مستوى المنصة:**
  - `admin`: إدارة الربط مع Basecamp وGoogle، كل الملفات، سجل المزامنة الكامل.
  - `editor`: إنشاء/استيراد/تعديل الملفات المصرّح له بها.
  - `viewer`: قراءة فقط.
- **صلاحيات الملف:** مالك + قائمة مستخدمين بدور (`editor`/`viewer`). الافتراضي: من له وصول لمشروع Basecamp المرتبط يُقترح إضافته.
- **هوية Basecamp — قرار معتمَد: كل تعديل يظهر في Basecamp باسم صاحبه.**
  - تسجَّل المنصة تطبيقاً واحداً في Basecamp (OAuth 2.0 عبر Launchpad)، ويربط **كل مستخدم حسابه الشخصي** مرة واحدة عند أول دخول (شاشة «اربط حسابك في Basecamp»).
  - الطلبات الصادرة تُنفَّذ **برمز المستخدم الذي أجرى التعديل**، فيظهر في Basecamp أنه هو من أنشأ المهمة أو عدّلها أو أنجزها.
  - مطابقة مستخدم `naf-id` بشخص Basecamp تلقائياً بالبريد الإلكتروني، مع شاشة مطابقة يدوية لـ `admin` لأي حالة لم تُطابَق.
  - **لا يُسمح بتحرير الأوراق المتزامنة قبل ربط الحساب** (الأوراق المحلية متاحة). يظهر شريط تنبيه واضح بزر الربط.
  - **رمز الخدمة:** حساب `admin` يُستخدم فقط للعمليات الخلفية التي لا صاحب بشري لها: إنشاء الـ Webhooks، والمطابقة الدورية (قراءة فقط)، وتحديث ذاكرة الأعضاء. **لا يُستخدم أبداً لكتابة تعديل نيابة عن مستخدم.**
  - إذا انتهت صلاحية رمز مستخدم وفشل تجديده: تبقى تعديلاته معلّقة (`pending`) مع تنبيه له بإعادة الربط، ولا تُرسل باسم حساب آخر.
  - صلاحيات المستخدم في Basecamp تسري كما هي: إن لم يكن عضواً في المشروع، أو كانت صلاحية الحذف مقصورة على المدراء ومنشئ العنصر، يُرفض الطلب (`403`/`404`) وتظهر له رسالة عربية واضحة على الصف.

## 4. البنية التقنية

### 4.1 المكدّس
| الطبقة | التقنية |
|---|---|
| الواجهة | React + TypeScript + Vite، مكوّنات `naf-ui` (shadcn)، خط ثمانية (Thmanyah) |
| محرك الجداول | Univer (`@univerjs/presets` — Sheets core) |

| قاعدة البيانات | Cloudflare D1 |
| تخزين الملفات واللقطات | Cloudflare R2 |
| الإعدادات والرموز المؤقتة | Cloudflare KV |
| التعاون اللحظي والأقفال | Durable Objects (كائن لكل Workbook) |
| مهام المزامنة | Cloudflare Queues (+ Dead Letter Queue) |
| المطابقة الدورية | Cron Triggers |
| الاستضافة | Cloudflare Pages (الواجهة) + Workers (API) على نطاق فرعي من `naflaw.sa` (يُحدَّد لاحقاً) |

> البنية على Cloudflare لتتسق مع الموقع وبقية منصات ناف.

### 4.2 المخطط العام

```
[المتصفح: React + Univer]
     │  WebSocket (تعديلات لحظية)        │ REST
     ▼                                    ▼
[Durable Object: WorkbookRoom] ◄──► [Worker API (Hono)] ◄── naf-id (SSO)
     │ لقطات/سجل عمليات                  │
     ▼                                    ├──► D1 (البيانات الوصفية والربط)
    R2                                    ├──► Queue: bc-outbound ──► Basecamp API
                                          ├──◄ Webhook: /webhooks/basecamp/:secret
                                          ├──► Google Sheets API (الاستيراد)
                                          └──► Cron: مطابقة كل 15 دقيقة
```

## 5. محرك الجداول (Univer)

### 5.1 الميزات المطلوبة (كلها من النسخة مفتوحة المصدر — تحقّق من كل واحدة في المرحلة 0)
- أوراق متعددة: إضافة/حذف/إعادة تسمية/ترتيب/إخفاء/تلوين التبويب.
- المعادلات، بما فيها المراجع بين الأوراق (`='ورقة'!A1`).
- تنسيق الخلايا: الخط، الحجم، اللون، التعبئة، الحدود، المحاذاة، الالتفاف، الدمج، تنسيقات الأرقام والتواريخ.
- عرض الأعمدة وارتفاع الصفوف، التجميد، الإخفاء.
- **التنسيق الشرطي** (`@univerjs/sheets-conditional-formatting`).
- **الفلترة والفرز** (`@univerjs/sheets-filter`, `sheets-sort`).
- **التحقق من البيانات والقوائم المنسدلة** (`@univerjs/sheets-data-validation`) — أساس عمود المسؤول.
- الروابط، الملاحظات/التعليقات على الخلايا.
- التراجع/الإعادة.
- **اتجاه الورقة من اليمين لليسار (RTL)** — **حرج: تحقّق من دعمه الفعلي في المرحلة 0.** إن كان ناقصاً فأبلغ فوراً بالبدائل.

### 5.2 مكوّنات مخصّصة نبنيها فوق Univer
- **محرّر خلية المسؤول:** قائمة منسدلة متعددة الاختيار بالاسم والصورة، مصدرها أعضاء مشروع Basecamp.
- **محرّر خلية المرفقات:** رقائق (chips) للملفات + زر رفع + سحب وإفلات.
- **عمود الحالة:** مربع اختيار (منجزة/غير منجزة).
- **مؤشر المزامنة لكل صف:** أيقونة صغيرة (متزامن ✓ / بانتظار ⏳ / خطأ ⚠) في هامش الصف.
- **الإزاحة الهرمية:** صفوف المهام الفرعية بإزاحة بصرية تحت المهمة الأم، مع طيّ/فتح.

### 5.3 حدود الترخيص — قرار معماري
وفق وثائق Univer، **الاستيراد/التصدير XLSX، والتعاون اللحظي، والجداول المحورية، والرسوم البيانية، والطباعة، وسجل النسخ** ضمن **Univer Pro** (ترخيص تجاري).

- **الاستيراد:** لا نحتاج Pro؛ نبني محوّلاً من **JSON واجهة Google Sheets** إلى `IWorkbookData` مباشرة (§7).
- **التعاون اللحظي:** خياران — **قرار مفتوح (§17-2):**
  - **(أ) بناء ذاتي:** بث أوامر/تحويلات Univer (Mutations) عبر Durable Object مع ترتيب خادمي للعمليات. أرخص ترخيصاً، أكثر جهداً.
  - **(ب) شراء Univer Pro** واستخدام خادم التعاون الخاص به.
  - **الافتراضي حتى القرار:** ابدأ بـ (أ) بنموذج مبسّط: الخادم مصدر الحقيقة، وقفل ناعم على مستوى الخلية الجاري تحريرها، وبث العمليات المطبّقة لكل المتصلين.
- **الرسوم البيانية والجداول المحورية:** خارج الإصدار الأول؛ تظهر في تقرير الاستيراد كعناصر لم تُنقل.

## 6. نموذج البيانات

### 6.1 مبدأ التخزين
- **محتوى الملف الكامل** (الخلايا، التنسيقات، المعادلات) = لقطة `IWorkbookData` في **R2** (`workbooks/{id}/snapshots/{version}.json`) + سجل عمليات منذ آخر لقطة داخل Durable Object. لقطة جديدة كل 200 عملية أو 5 دقائق خمول.
- **البيانات الوصفية وحالة الربط** = **D1**.
- **هوية الصف الثابتة:** كل صف مهمة يحمل معرّفاً داخلياً `task_uid` (UUID) في **عمود نظام مخفي ومحمي** في الورقة (`__uid`)، ومعه `__parent_uid` و`__level`. الاعتماد على رقم الصف ممنوع لأن الإدراج والفرز يغيّرانه.

## 7. الإنشاء والاستيراد

### 7.1 شاشة «ملف جديد»
ثلاثة خيارات:
1. **ملف فارغ** — ورقة واحدة بأعمدة افتراضية: `المهمة | المسؤول | تاريخ البدء | تاريخ الاستحقاق | الحالة | المرفقات | ملاحظات`.
2. **من قالب ناف** — قوالب يحفظها `admin` (أي ملف يُحوَّل إلى قالب).
3. **استيراد من Google Sheets** — عبر Google Picker أو لصق رابط.

### 7.2 الاستيراد من Google Sheets
- **OAuth Google** بأضيق نطاق ممكن: `drive.file` (مع Picker) أو `spreadsheets.readonly`. **الملف الأصلي لا يُعدَّل إطلاقاً.**
- جلب: `spreadsheets.get` مع `includeGridData=true` وقناع حقول (fields mask) محدد، مع التقسيم إن كان الملف كبيراً.
- **المحوّل (`packages/gsheets-import`)** يحوّل إلى `IWorkbookData`:

| من Google Sheets | إلى Univer | ملاحظة |
|---|---|---|
| `sheets[].properties` (title, index, hidden, tabColor, rightToLeft, gridProperties.frozen*) | خصائص الورقة | |
| `rowData[].values[].userEnteredValue` (قيم ومعادلات) | `cellData.v / .f` | المعادلة كما كُتبت |
| `userEnteredFormat` (خط، لون، تعبئة، حدود، محاذاة، التفاف، numberFormat) | `styles` + `cellData.s` | توحيد الأنماط المتكررة |
| `textFormatRuns` | نص غني (rich text) | |
| `rowMetadata/columnMetadata.pixelSize`, `hiddenByUser` | ارتفاع/عرض/إخفاء | |
| `merges` | `mergeData` | |
| `conditionalFormats` (boolean + gradient) | قواعد التنسيق الشرطي | |
| `dataValidation` | قواعد التحقق | |
| `basicFilter` | فلتر الورقة | |
| `filterViews` | — | تقرير: غير منقول (الإصدار 1) |
| `note`, `hyperlink` | ملاحظة / رابط | |
| `charts`, `pivotTable`, `slicers`, `bandedRanges`, الصور | — | تقرير: غير منقول (`bandedRanges` تُحوَّل لتعبئة ثابتة إن أمكن) |
| `protectedRanges` | — | تقرير: غير منقول |

- **المعادلات غير المدعومة:** بعد التحويل، مرّر كل معادلة على محرك Univer؛ أي دالة غير معروفة (مثل `IMPORTRANGE`, `GOOGLEFINANCE`, `IMAGE`, `SPARKLINE`) → تُحفظ **القيمة المحسوبة الأخيرة** (`effectiveValue`) في الخلية مع ملاحظة على الخلية بالمعادلة الأصلية، وتُدرج في التقرير.
- **تقرير الاستيراد:** شاشة واضحة بعد الاستيراد: عدد الأوراق/الخلايا/المعادلات المنقولة، وقائمة بكل ما لم يُنقل أو نُقل كقيمة ثابتة، مع موقعه (ورقة!خلية) ورابط للانتقال إليه.
- **(لاحقاً، اختياري)** رفع ملف `.xlsx` عبر مكتبة تحليل مفتوحة (ExcelJS) إلى المحوّل نفسه.

### 7.3 معالج الربط بعد الإنشاء/الاستيراد
1. **ربط الملف بمشروع:** اختيار مشروع Basecamp موجود (قائمة من الحساب) أو «إنشاء مشروع جديد بالاسم نفسه»، أو «بدون ربط الآن».
2. **لكل ورقة:** `مزامنة مع قائمة موجودة` / `إنشاء قائمة جديدة باسم الورقة` / `ورقة محلية (بدون مزامنة)`.
3. **صف العناوين:** اكتشاف تلقائي (الافتراضي الصف 1) مع إمكانية التعديل.
4. **مطابقة الأعمدة:** اقتراح تلقائي بالمرادفات العربية والإنجليزية، مثل:
   - title: المهمة، العنوان، البند، النشاط، Task
   - assignees: المسؤول، المكلف، المنفذ، Owner, Assignee
   - due_on: تاريخ الاستحقاق، الموعد النهائي، تاريخ الإنجاز، Due
   - starts_on: تاريخ البدء، Start
   - completed: الحالة، منجز، تم، Done, Status
   - notes: ملاحظات، الوصف، التفاصيل
   - attachments: المرفقات، الملفات
   - الباقي: «عمود حر» مع خيار «إلحاقه بوصف المهمة في Basecamp».
5. **الهرمية في الملف المستورد:** اكتشاف المهام الفرعية إن وُجد عمود ترقيم (1، 1.1، 1.2) أو إزاحة نصية بادئة؛ وإلا تُعامل كل الصفوف مهاماً رئيسية مع إمكانية الإزاحة لاحقاً.
6. **قيم عمود الحالة:** إن كان نصياً («منجز/قيد التنفيذ/متأخر») تُحدَّد القيمة التي تعني «منجزة»، وتبقى القيم الأخرى في المنصة.
7. **قيم عمود المسؤول:** مطابقة الأسماء النصية الموجودة مع أعضاء Basecamp (تطابق تقريبي) وعرض غير المطابَق للتأكيد اليدوي.
8. **عند الربط بقائمة فيها مهام مسبقاً:** خياران — «إنشاء كل الصفوف كمهام جديدة» أو «مطابقة بالعنوان مع مراجعة يدوية قبل الاعتماد». **لا يُحذف أي شيء من Basecamp في هذه المرحلة.**
9. **معاينة نهائية** بعدد المهام والمهام الفرعية التي ستُنشأ، ثم زر «بدء المزامنة».

## 8. أعمدة النظام والهرمية

- أعمدة مخفية ومحمية في كل ورقة متزامنة: `__uid`, `__parent_uid`, `__level`. لا يحرّرها المستخدم.
- **الإزاحة:** `Tab` (أو زر «تحويل لمهمة فرعية») على صف ← يصبح فرعياً للصف الرئيسي الذي فوقه. `Shift+Tab` ← يعود رئيسياً.
- **حد المستوى:** مهام Basecamp 5 الفرعية **مستوى واحد فقط**. أي محاولة لإزاحة مستوى ثالث تُمنع برسالة واضحة.
- **نقل مهمة رئيسية** (سحب الصف) ينقل مهامها الفرعية معها.
- **عمود تقدّم محسوب اختياري** في الصف الرئيسي: «3 من 5» حسب الفرعية المنجزة.
- **إنجاز المهمة الأم لا يُنجز الفرعية تلقائياً والعكس** (مطابقة لسلوك Basecamp 5)؛ مع خيار إعداد «اقترح إنجاز الأم عند إنجاز كل الفرعية».

### ما يُزامَن لكل مستوى
| الحقل | مهمة (To-do) | مهمة فرعية (Subtask) |
|---|---|---|
| العنوان | ✓ (`content`) | ✓ (`title`) |
| المسؤول (متعدد) | ✓ (`assignee_ids`) | ✓ (`assignee_ids`) |
| تاريخ الاستحقاق | ✓ (`due_on`) | ✓ (`due_on`) |
| تاريخ البدء | ✓ (`starts_on`) | ✗ غير موجود في Basecamp — يبقى محلياً |
| الحالة (منجزة) | ✓ | ✓ |
| الوصف/الملاحظات | ✓ (`description`) | ✗ غير موجود — يبقى محلياً |
| المرفقات | ✓ (داخل الوصف) | ✗ غير موجود — تُعرض محلياً مع تنبيه، أو تُرفق بالأم بإشارة للفرعية (إعداد) |
| الترتيب | ✓ (ويمكن نقلها لقائمة أخرى) | ✓ (داخل أمها فقط) |
| التعليقات | ✓ | ✗ — على المهمة الأم فقط |
| الحذف | سلة المهملات (قابل للاسترجاع) | **حذف نهائي** (لا سلة) — انظر §9.2 |

> الخلايا غير المتزامنة في صفوف المهام الفرعية تُميَّز بصرياً (خلفية مخطّطة خفيفة + تلميح «لا يُزامَن مع Basecamp»).

### 8.1 الإسناد التلقائي للمهمة الرئيسية من مهامها الفرعية
**القاعدة:** إذا لم يُسنَد أحد للمهمة الرئيسية يدوياً، فمسؤولوها = **اتحاد مسؤولي كل مهامها الفرعية** (بلا تكرار)، في الورقة وفي Basecamp معاً.

- **وضع الإسناد** لكل مهمة رئيسية: `auto` (تلقائي) أو `manual` (يدوي)، ويُحفظ في `tasks.assign_mode`.
  - الافتراضي لأي مهمة رئيسية جديدة بلا مسؤول: `auto`.
  - إسناد شخص للمهمة الرئيسية يدوياً (من الورقة أو من Basecamp) ← تصبح `manual`، وتتوقف إعادة الحساب.
  - إفراغ خلية المسؤول في المهمة الرئيسية ← تعود `auto` ويُعاد الحساب فوراً.
- **متى يُعاد الحساب (في وضع `auto` فقط):** إضافة مهمة فرعية أو حذفها، أو تغيير مسؤولي أي فرعية، أو نقل فرعية من مهمة لأخرى — سواء حدث التغيير في الورقة أو وصل من Basecamp (`kanban_step_created`, `kanban_step_assignment_changed`, `kanban_step_trashed/deleted`).
- **المهام الفرعية المنجزة:** مسؤولوها يبقون ضمن الاتحاد (الافتراضي)، مع إعداد على مستوى الورقة: «استبعد مسؤولي المهام الفرعية المنجزة».
- **مهمة رئيسية بلا فرعيات وبلا مسؤول:** تبقى بلا مسؤول.
- **في Basecamp:** يُرسل التحديث بـ `PUT /todos/{id}.json` (بكل الحقول كالعادة) مع `"notify": false`، لأن المسؤولين أُشعروا أصلاً عند إسناد المهام الفرعية لهم، فلا إشعار مكرر.
- **بأي رمز يُرسل التحديث:** برمز المستخدم الذي أحدث التغيير في الفرعية (من المنصة، أو صاحب الحدث `creator` إن كان قد ربط حسابه). إن لم يتوفر رمز له، يُرسل **برمز الخدمة** كاستثناء وحيد موثّق لقاعدة §3، لأنه إجراء آلي لا تعديل بشري، ويُسجَّل في السجل بوصف «قاعدة تلقائية».
- **منع الحلقات:** التحديث الذي ترسله المنصة يعود كحدث `todo_assignment_changed`؛ إذا طابق المسؤولون الاتحاد المحسوب يبقى الوضع `auto` ولا يُتخذ إجراء. إذا اختلفوا فهذا تعديل بشري ← `manual`.
- **في الواجهة:** المسؤولون التلقائيون يظهرون في الخلية برقائق بإطار منقّط وتلميح «تلقائي من المهام الفرعية»، والإسناد اليدوي برقائق عادية. خيار في قائمة الخلية: «اجعله تلقائياً» لإعادة مهمة `manual` إلى `auto`.
- **إعداد عام للورقة:** «الإسناد التلقائي للمهام الرئيسية» (مفعّل افتراضياً) يمكن إيقافه لورقة بعينها.
- **حدّ واعٍ:** وفق هذه القاعدة لا يمكن إبقاء مهمة رئيسية بلا مسؤول عمداً إذا كان لفرعياتها مسؤولون؛ إن احتيج ذلك يُوقف الإعداد للورقة.
- **الاتحاد يشمل الجهات الخارجية والمتابعين الداخليين** (§8.2): الخارجيون يُضافون للرئيسية محلياً، والمتابعون الداخليون يُضافون لها في Basecamp.

### 8.2 الإسناد لأشخاص من خارج المشروع أو خارج Basecamp (معتمَد)
خلية المسؤول تقبل ثلاثة أنواع من الأشخاص، وتعرض عند البحث فيها أقساماً: «أعضاء المشروع»، «أعضاء الحساب (خارج المشروع)»، «جهات خارجية»، ثم «+ إضافة شخص جديد».

#### الحالة 1 — عضو في حساب Basecamp وليس في المشروع
- القائمة تعرضه في قسم «أعضاء الحساب» (من `GET /people.json` بذاكرة مؤقتة).
- عند اختياره: حوار «فلان ليس عضواً في مشروع (اسم المشروع). إضافته تمنحه الوصول لكل محتوى المشروع. أضيفه؟».
- الموافقة ← `PUT /projects/{id}/people/users.json` مع `grant: [id]` برمز المستخدم ← ثم الإسناد.
- إن لم يملك المستخدم صلاحية إدارة الأشخاص (`403`): رسالة «لا تملك صلاحية إضافة أعضاء للمشروع؛ اطلب ذلك من مدير المشروع»، مع زر «أرسل طلباً» يُنشئ إشعاراً لـ `admin` في المنصة، ويبقى الصف معلقاً بحالة «بانتظار إضافة عضو».

#### الحالة 2 — شخص جديد يُدعى إلى Basecamp
من «+ إضافة شخص جديد» ← اختيار «دعوة إلى Basecamp» بأحد نوعين:
- **عضو فريق:** `POST /account/enrollments/people.json` مع `project_ids: [المشروع]` و`notify: true`. تنبيه قبل التأكيد: «سيُحسب ضمن مستخدمي حساب Basecamp». عند `507` (بلوغ حد المستخدمين): رسالة واضحة واقتراح إضافته جهةً خارجية بدلاً من ذلك.
- **عميل (Client):** متاح فقط إن كان العملاء مفعّلين في المشروع ← `PUT /projects/{id}/people/client_users.json` مع `create`. إن لم يكونوا مفعّلين: **لا تفعّلهم المنصة تلقائياً**؛ تعرض رسالة بأن التفعيل يغيّر ظهور أدوات المشروع للعملاء ويجب أن يقرره مدير المشروع من Basecamp (أو `admin` من إعدادات المنصة بعد تأكيد صريح).
- الصلاحية: الدعوة متاحة لأدوار `admin` في المنصة فقط افتراضياً (إعداد).
- بعد نجاح الدعوة: يُضاف الشخص للمشروع ويُسند فوراً، حتى قبل قبوله الدعوة.

#### الحالة 3 — جهة خارجية (الخيار الافتراضي لمن هم خارج Basecamp)
- **سجل الجهات الخارجية** على مستوى المنصة: الاسم، الجهة/الشركة، البريد، الجوال، ملاحظة. يُضاف من الخلية مباشرة («+ إضافة شخص جديد» ← «جهة خارجية») أو من صفحة إدارة الجهات.
- يظهر في خلية المسؤول برقاقة مميزة (لون مختلف + أيقونة «خارجي»)، ويُعامل في الفلترة والفرز والتقارير ولوحات الإنجاز كأي مسؤول.
- **المزامنة إلى Basecamp:**
  - **مهمة رئيسية:** تُكتب الجهات الخارجية في **الكتلة المُدارة** داخل وصف المهمة (انظر أدناه) بسطر: «مسؤولون خارجيون: فلان (الجهة)، فلان (الجهة)». أعضاء Basecamp في الخلية نفسها يُرسلون في `assignee_ids` كالعادة.
  - **مهمة فرعية:** لا وصف لها في Basecamp؛ الجهة الخارجية تبقى ظاهرة في المنصة فقط.
- **المتابع الداخلي (إلزامي):** إذا كانت كل مسؤوليات مهمة (رئيسية أو فرعية) لجهات خارجية فقط، **تشترط المنصة تحديد متابع داخلي** من أعضاء المشروع قبل حفظ الإسناد:
  - يُسند المتابع في Basecamp (`assignee_ids`) فلا تبقى المهمة بلا مسؤول هناك.
  - يظهر في الخلية برقاقة «متابع» بجانب الجهة الخارجية.
  - إن أُضيف لاحقاً عضو Basecamp مسؤولاً مباشراً للمهمة، يُسأل المستخدم: «هل تُبقي فلان متابعاً؟».
  - إن أُزيلت الجهة الخارجية، يتحول المتابع إلى مسؤول عادي (مع إمكانية إزالته).
- **إشعار الجهة الخارجية بالبريد (اختياري لكل إسناد، مفعّل افتراضياً):**
  - عند الإسناد: بريد عربي بهوية ناف يحوي عنوان المهمة، الموعد، اسم المشروع، اسم المتابع الداخلي ووسيلة التواصل معه. **لا روابط للمنصة ولا بيانات داخلية أخرى.**
  - تذكير قبل الموعد بيومين (إعداد) وعند التأخر (إعداد).
  - المرسل: عنوان من نطاق `naflaw.sa` (يُحدَّد)، ومزوّد الإرسال قرار مفتوح (§17-7).
  - **إنجاز مهمة الجهة الخارجية** يحدّثه المتابع الداخلي أو أي محرر في المنصة (لا تملك الجهة الخارجية وصولاً للمنصة في الإصدار الأول).

#### الكتلة المُدارة في وصف المهمة (Managed block)
لتجميع كل ما تكتبه المنصة في وصف المهمة دون العبث بما يكتبه الناس:
- كتلة واحدة في **آخر** الوصف، تبدأ بخط فاصل ثم عنوان عريض ثابت «بيانات من منصة الاتصال المؤسسي» وتحته الأسطر: المسؤولون الخارجيون، المتابع الداخلي، والأعمدة الحرة المضبوطة على «إلحاق بالوصف» (§7.3).
- عند الإرسال: تُستبدل الكتلة كاملة، ويُحفظ ما قبلها كما هو حرفياً (بما فيه المرفقات).
- عند الاستقبال: تُفصل الكتلة ولا تُعامل كنص كتبه مستخدم؛ وإن عدّلها أحد يدوياً في Basecamp تُعاد كتابتها من المنصة مع تسجيل ذلك في السجل.
- استخدم فقط وسوم HTML المسموحة في دليل Rich text الرسمي، واختبر في المرحلة 0 أن الكتلة تبقى سليمة بعد الحفظ في Basecamp.

## 9. محرّك المزامنة (`packages/sync-engine`)

### 9.1 المبادئ
- **منطق نقي قابل للاختبار:** دالة `diff(localRow, lastSynced, remoteState) → actions[]` بلا آثار جانبية؛ التنفيذ في طبقة منفصلة.
- **وحدة التعارض = الحقل** لا الصف.
- **قاعدة التعارض:** آخر تعديل يغلب (Last-Writer-Wins) بمقارنة `updated_at` البعيد بوقت التعديل المحلي، **مع تسجيل كل تعارض** في `sync_log` وإظهار تنبيه على الخلية يمكن منه استعادة القيمة الأخرى.
- **منع الصدى (Echo suppression):** عند استقبال Webhook لتعديل أرسلته المنصة نفسها، يُقارن `hash` الحقول مع `last_synced_hash` فيُتجاهل.
- **Idempotency:** كل مهمة صادرة تحمل مفتاحاً فريداً؛ إعادة المحاولة لا تُنشئ مهمة مكررة (تحقّق من وجود `bc_recording_id` قبل الإنشاء، واحفظه فور نجاح الإنشاء).

### 9.2 الاتجاه الصادر (المنصة ← Basecamp)
1. تعديل خلية في عمود مربوط ← الـ Durable Object يحدّد `task_uid` المتأثر.
2. **تجميع (debounce) 2 ثانية** لكل مهمة، ثم رسالة إلى `Queue: bc-outbound`.
3. المستهلك يبني الحالة الكاملة للمهمة ويستدعي Basecamp **برمز المستخدم صاحب التعديل** (§3).
4. ⚠ **سلوكان مختلفان للتحديث (مُتحقَّق منهما):**
   - **المهمة (To-do):** `PUT /todos/{id}.json` **يمسح أي حقل غير مُرسل** (مثلاً عدم إرسال `assignee_ids` يزيل كل المسؤولين). لذا: اجلب الحالة الحالية أو استخدم آخر حالة متزامنة، وأرسل **كل الحقول** (`content`, `description`, `assignee_ids`, `completion_subscriber_ids`, `due_on`, `starts_on`) في كل تحديث. `content` إلزامي دائماً.
   - **المهمة الفرعية (Subtask):** `PUT /subtasks/{id}.json` **تحديث جزئي**؛ أرسل الحقل المعدَّل فقط. لمسح التاريخ أرسل `"due_on": null`، ولإزالة كل المسؤولين `"assignee_ids": []`.
5. الإنجاز/إلغاء الإنجاز عبر نقطة `completion` المخصصة (POST/DELETE) لا عبر التحديث العام.
6. الترتيب عبر نقطة `position` (يبدأ من 1). نقل مهمة بين ورقتين = نفس النقطة مع `parent_id` للقائمة الجديدة (ضمن المشروع نفسه فقط).
7. **حذف صف مهمة رئيسية** ← حوار تأكيد ← نقلها إلى **سلة المهملات** في Basecamp (قابلة للاسترجاع).
   **حذف صف مهمة فرعية** ← حذف Basecamp لها **نهائي بلا سلة**، لذا: حوار تأكيد بصياغة صريحة («سيُحذف نهائياً من Basecamp ولا يمكن استرجاعه»)، وحفظ نسخة كاملة من بياناتها في سجل المنصة قبل الحذف، والتراجع (Ctrl+Z) يعيد إنشاءها كمهمة فرعية جديدة.
   **حذف مهمة رئيسية لها فرعية:** تُنقل الأم للسلة ومعها فرعياتها (لا تُحذف الفرعية منفصلة).
8. نجاح ← تحديث `last_synced_hash` و`sync_state='synced'`. فشل ← إعادة محاولة بتراجع أسّي (حتى 5)، ثم DLQ و`sync_state='error'` مع رسالة عربية مفهومة على الصف.
9. **حدود المعدل:** الحد الشائع الأول نحو **50 طلباً كل 10 ثوانٍ لكل عنوان IP**، مع حدود أخرى متغيرة. احترم `429` وانتظر ثواني `Retry-After`، وأعد محاولة `5xx` بتراجع أسّي، **ولا تُعد محاولة `404`** (عنصر محذوف أو صلاحية ناقصة؛ وإن جاءت بترويسة `Reason: Account Inactive` أوقف مزامنة الحساب كله ونبّه `admin`). عميل Basecamp يطبّق طابوراً بحد آمن (مثلاً 4 طلبات/ثانية) مشتركاً لكل العمليات.
10. **ترويسات إلزامية:** `User-Agent: NAF Comms (info@naflaw.sa)` في كل طلب (بدونه `400`)، و`Content-Type: application/json; charset=utf-8` في POST/PUT (بدونه `415`).

### 9.3 الاتجاه الوارد (Basecamp ← المنصة)
1. عند ربط ملف بمشروع: إنشاء **Webhook** على المشروع (برمز الخدمة) بالأنواع: `["Todo", "Todolist", "Kanban::Step", "Comment", "Upload"]`. ملاحظة: المهام الفرعية تصل بنوع `Kanban::Step`.
2. عنوان الاستقبال: `/webhooks/basecamp/:secret` بسرّ عشوائي لكل مشروع. الوثائق **لا تذكر توقيعاً** للطلبات، لذا: السرّ في المسار + التحقق من أن `recording.bucket.id` يطابق المشروع المرتبط بهذا السرّ + **جلب السجل من الواجهة البرمجية دائماً**.
3. استجب `200` فوراً، وأرسل الحدث لطابور داخلي للمعالجة. Basecamp يعيد المحاولة حتى 10 مرات بتراجع أسّي ثم **يعطّل الـ Webhook**، ولا يتبع إعادة التوجيه 3xx. المطابقة الدورية تفحص `active` لكل Webhook وتعيد تفعيله.
4. المعالجة: **حمولة الـ Webhook لا تحتوي** `description` ولا `completed` ولا `assignees`، لذا اجلب السجل كاملاً (`GET /todos/{id}.json` أو `GET /subtasks/{id}.json`) ← `diff` ← تطبيقه عبر Durable Object الخاص بالملف ← بث للمتصفحات المفتوحة ← لقطة.
5. **أنواع الأحداث (`kind`) الموثّقة** وما تفعله المنصة:
   - `todo_created`, `kanban_step_created` ← إنشاء صف.
   - `todo_title_updated`, `todo_content_updated`, `kanban_step_title_updated` ← تحديث.
   - `todo_completed`, `todo_uncompleted` ← تحديث الحالة.
   - `todo_assignment_changed`, `kanban_step_assignment_changed` ← تحديث المسؤولين (في `details`: `added_person_ids`, `removed_person_ids`).
   - `*_archived`, `*_trashed`, `*_deleted` ← تعليم الصف (البند 10 أدناه)؛ `*_unarchived`, `*_untrashed` ← إعادته.
   - `todolist_created` ← ورقة جديدة حسب الإعداد.
   - `comment_created` ← تحديث عدّاد التعليقات ولوحة التفاصيل.
   - `*_copied`, `*_inserted` ← تحديث شامل للقائمة المعنية.
   - **أي `kind` غير معروف** ← جلب السجل وتطبيق `diff` عام (لا تفشل).
6. ⚠ **فجوات في التوثيق تُختبر في المرحلة 0:** الوثائق لا تذكر صراحة حدثاً لتغيير تاريخ الاستحقاق، ولا لإنجاز المهمة الفرعية. افترض أنها قد لا تصل، واعتمد على: (أ) جلب المهمة كاملة عند أي حدث عليها أو على فرعياتها، (ب) المطابقة الدورية (§9.4).
7. ⚠ **التغييرات المنتشرة للأبناء لا تُرسل:** أرشفة قائمة لا ترسل حدثاً لكل مهمة فيها، بل حدثاً واحداً للقائمة. عند `todolist_archived/trashed` طبّق الحالة على كل صفوف الورقة.
8. **مهمة جديدة أُنشئت في Basecamp** ← صف جديد في الورقة المرتبطة بقائمتها، في الموضع الموافق لترتيبها، وتحته مهامها الفرعية إن وُجدت (من `GET /recordings/{id}/subtasks.json` مرتباً حسب الموضع).
9. **قائمة جديدة أُنشئت في Basecamp** ← حسب إعداد الملف: «أنشئ ورقة جديدة تلقائياً» (الافتراضي) أو «تجاهل».
10. **مهمة حُذفت/أُرشفت في Basecamp** ← الصف يُعلَّم «محذوفة في Basecamp» (نص مشطوب + لون رمادي)، ولا يُحذف من الورقة إلا بإجراء المستخدم.
11. **مهمة نُقلت لقائمة أخرى** (يتغير `parent` في السجل) ← نقل الصف ومهامه الفرعية للورقة المقابلة (أو إلى ورقة «غير مصنّف» إن كانت القائمة غير مربوطة).

### 9.4 المطابقة الدورية (Reconciliation)
- **Cron كل 15 دقيقة:** لكل قائمة مربوطة، جلب `GET /todolists/{id}/todos.json` (والمنجزة بـ `?completed=true`) مع `If-None-Match` بآخر `ETag` محفوظ؛ استجابة `304` تعني لا تغيير ولا تستهلك معالجة. لكل مهمة تغيّر `updated_at` أو `subtasks_completed_count` أو `subtasks_count`: اجلبها وفرعياتها وطبّق `diff`.
- **انتبه للترقيم:** النتائج مقسّمة صفحات؛ اتبع ترويسة `Link` (rel="next") ولا تبنِ روابط الصفحات يدوياً. حقل `steps` في المهمة يحمل أول 100 فرعية فقط؛ إن كان `subtasks_count` أكبر فاجلب من `subtasks_url`.
- **زر «مزامنة الآن»** في إعدادات الملف.
- **تقرير صحة المزامنة** لـ `admin`: عدد الأخطاء، التعارضات، آخر نجاح، حالة الـ Webhooks.

### 9.5 أعضاء المشروع (للقائمة المنسدلة)
- تُجلب من نقطة أعضاء المشروع وتُخزَّن في `bc_people_cache`.
- تحديث: عند فتح الملف إن تجاوز عمر الذاكرة 10 دقائق + في كل مطابقة دورية.
- عضو أُزيل من المشروع وما زال مسنداً لمهام ← يظهر في الخلية برقاقة رمادية مع تنبيه.

## 10. المرفقات

- **رفع من المنصة:** الملف ← R2 (نسخة ناف) ← رفعه إلى Basecamp عبر نقطة المرفقات للحصول على `attachable_sgid` ← تضمينه في وصف المهمة كعنصر مرفق (bc-attachment) ← إعادة إرسال الوصف كاملاً.
- **وارد من Basecamp:** تحليل وصف المهمة ورفوعات المشروع المرتبطة بها لاستخراج المرفقات ← عرضها رقائق في الخلية، والتنزيل عبر وكيل في الـ Worker (بصلاحيات المستخدم).
- **الحد الأقصى للحجم:** يُضبط في الإعدادات (افتراضي 100MB)، مع رسالة واضحة عند التجاوز.
- **الحذف:** إزالة رقاقة ← إزالة المرفق من الوصف في Basecamp بعد تأكيد؛ نسخة R2 تبقى في الأرشيف 30 يوماً.

## 11. التعاون اللحظي

- **Durable Object `WorkbookRoom`** لكل ملف: مصدر الحقيقة لحالة الملف أثناء الجلسة.
- اتصال WebSocket لكل متصفح؛ الخادم يرتّب العمليات ويبثها.
- **الحضور (Presence):** صور المستخدمين المتصلين أعلى الملف، وإطار ملوّن حول الخلية التي يحرّرها كل مستخدم.
- **قفل ناعم:** الخلية قيد التحرير من مستخدم تظهر مقفلة للآخرين حتى ينتهي.
- انقطاع الاتصال ← وضع «للقراءة فقط» مع شريط تنبيه، وإعادة اتصال تلقائية ومزامنة ما فات.
- (انظر §5.3 لقرار البناء الذاتي مقابل Univer Pro.)

## 12. الواجهة

### 12.1 الشاشات
1. **الرئيسية — قائمة الملفات:** بطاقات/جدول بالعنوان، المشروع المرتبط، عدد الأوراق، نسبة الإنجاز، آخر تعديل، حالة المزامنة. بحث وفلترة. زر «ملف جديد».
2. **محرّر الملف:** شريط أدوات مطابق لـ Google Sheets (بالعربية)، شريط المعادلات، التبويبات أسفل الشاشة (من اليمين)، مؤشر المزامنة العام أعلى الشاشة.
3. **لوحة إعدادات الملف (جانبية):** الربط بالمشروع، أعضاء المنصة وصلاحياتهم، سلوك القوائم الجديدة، زر «مزامنة الآن».
4. **لوحة إعدادات الورقة (جانبية، من قائمة التبويب):** وضع المزامنة، القائمة المرتبطة، صف العناوين، مطابقة الأعمدة، معنى «منجزة» في عمود الحالة.
5. **لوحة تفاصيل المهمة (عند فتح صف):** كل الحقول، المهام الفرعية، المرفقات، **تعليقات Basecamp** (قراءة وإضافة)، سجل تغييرات الصف، رابط «فتح في Basecamp».
6. **سجل المزامنة:** جدول قابل للفلترة بالملف والمستخدم والاتجاه والحالة.
7. **تقرير الاستيراد** (§7.2).
8. **الإعدادات العامة (`admin`):** ربط Basecamp، ربط Google، القوالب، حدود المرفقات.

### 12.2 الهوية والتجربة
- RTL كامل، خط ثمانية، رموز الألوان والمسافات من `naf-ui` (لا قيم ألوان مباشرة).
- أيقونات Lucide فقط.
- الأرقام اللاتينية في الخلايا والتواريخ (افتراضي)، والتواريخ الميلادية بصيغة `YYYY-MM-DD` مع خيار عرض هجري في الإعدادات.
- اختصارات لوحة المفاتيح مطابقة لـ Google Sheets.
- كل رسائل الخطأ بالعربية وبصياغة تشرح ما حدث وما المطلوب.
- يعمل على المتصفحات الحديثة، ومتجاوب للآيباد؛ على الجوال وضع عرض وتحرير مبسّط.

## 13. التكامل مع منظومة ناف

- **`naf-id`:** تسجيل الدخول الموحد، ومزامنة بيانات المستخدم (الاسم، البريد، الصورة) عند كل دخول.
- **`naf-ui`:** استيراد المكوّنات والرموز من السجل وفق نسخه الدلالية.
- **واجهة برمجية داخلية للمنظومة** (محمية برموز خدمة):
  - `GET /api/v1/workbooks` — قائمة الملفات وحالتها.
  - `GET /api/v1/workbooks/:id/tasks?status=&assignee=&due_before=` — المهام بصيغة موحدة.
  - `GET /api/v1/stats` — مؤشرات عامة (منجزة/متأخرة/حسب المسؤول) للوحات ناف.
  - Webhook صادر اختياري لأحداث: مهمة أُنجزت، مهمة تأخرت.
- **قرار مفتوح (§17-3):** ما الأنظمة الداخلية الأخرى التي يجب ربطها في الإصدار الأول؟

## 14. الأمان والخصوصية

- كل الرموز مشفّرة (AES-GCM) بمفتاح في Worker Secrets.
- أضيق نطاقات OAuth ممكنة لـ Google.
- التحقق من صلاحية المستخدم على الملف في كل طلب وكل اتصال WebSocket.
- Webhooks: سرّ في المسار + التحقق بجلب السجل من المصدر.
- سجل تدقيق (Audit) غير قابل للتعديل لكل عمليات الحذف والربط وتغيير الصلاحيات.
- نسخ احتياطي: لقطات R2 بإصدارات + تصدير D1 يومي.
- لا تُسجَّل محتويات المرفقات أو الرموز في السجلات.

## 15. مراحل التنفيذ ومعايير القبول

### المرحلة 0 — اختبار الجدوى (Spike) — **إلزامية قبل أي بناء**
- [ ] Univer مفتوح المصدر: ورقة RTL بنص عربي وخط ثمانية، تنسيق شرطي، فلتر، قائمة منسدلة، معادلة بين ورقتين.
- [ ] تحويل ملف Google Sheets حقيقي متعدد الأوراق (يزوّده فريق ناف) إلى Univer ومقارنته بصرياً.
- [ ] Basecamp 5 (الواجهة البرمجية موثّقة في الملحق أ؛ المطلوب **اختبار حيّ** لما لا تكشفه الوثائق): أنشئ مهمة ومهمة فرعية في مشروع تجريبي، ثم من واجهة Basecamp غيّر: تاريخ المهمة، تاريخ الفرعية، أنجز الفرعية، أعد ترتيبها، احذفها. **سجّل أي `kind` يصل لكل تغيير وما لا يصل شيء عنه.** النتيجة تحدد اعتماد المزامنة الواردة على الـ Webhook أو على المطابقة الدورية لكل حقل.
- **المخرج:** تقرير قصير بالنتائج وأي فجوة تغيّر هذه المواصفات، **وانتظار الاعتماد**.

### المرحلة 1 — الأساس
- مستودع، Workers/Pages/D1/R2، تسجيل الدخول بـ `naf-id`، الصلاحيات، شاشة الملفات، إنشاء ملف فارغ، محرّر Univer بحفظ واستعادة لقطات.
- **قبول:** مستخدمان يدخلان، ينشئ أحدهما ملفاً بثلاث أوراق وتنسيقات، يغلقه ويعيد فتحه فيجده كما هو.

### المرحلة 2 — الاستيراد
- Google OAuth + Picker، المحوّل، تقرير الاستيراد.
- **قبول:** استيراد ملف من 7 أوراق بتنسيق شرطي وفلاتر ومعادلات بين الأوراق؛ تطابق بصري ≥ 95% بتقييم الفريق؛ كل ما لم يُنقل مذكور في التقرير.

### المرحلة 3 — المزامنة الصادرة
- ربط Basecamp، معالج الربط، مطابقة الأعمدة، القائمة المنسدلة للمسؤولين، الإنشاء والتحديث والإنجاز والترتيب والحذف إلى السلة.
- **قبول:** تعديل العنوان والمسؤول والتاريخ والحالة في الورقة يظهر في Basecamp خلال 10 ثوانٍ؛ لا مهام مكررة عند انقطاع الشبكة وإعادة المحاولة.

### المرحلة 4 — المزامنة الواردة
- Webhooks، المعالجة، المطابقة الدورية، التعارضات، سجل المزامنة.
- **قبول:** تعديل في Basecamp يظهر في الورقة المفتوحة خلال 10 ثوانٍ بلا تحديث للصفحة؛ تعديل متزامن للحقل نفسه من الطرفين يُسجَّل تعارضاً قابلاً للاستعادة؛ إيقاف الـ Webhook يدوياً ثم التعديل في Basecamp يُلتقط في المطابقة الدورية.

### المرحلة 5 — المهام الفرعية، الإسناد المتقدم (§8.1، §8.2)، المرفقات، التعليقات
- يشمل: الإسناد التلقائي للرئيسية، الحالات الثلاث للإسناد من الخارج، المتابع الداخلي، الكتلة المُدارة، بريد الجهات الخارجية، وسيناريوهات الاختبار 13–24.
- **قبول:** إزاحة صف تنشئ مهمة فرعية في Basecamp بمسؤولها وتاريخها؛ إنشاء مهمة فرعية في Basecamp يظهر صفاً مزاحاً تحت أمها؛ رفع مرفق من الخلية يظهر في المهمة في Basecamp والعكس؛ قراءة وإضافة تعليق من لوحة التفاصيل.

### المرحلة 6 — التعاون اللحظي
- **قبول:** ثلاثة مستخدمين يحرّرون الملف نفسه؛ يرى كل منهم تعديلات الآخرين وحضورهم لحظياً؛ لا فقد للبيانات عند انقطاع أحدهم وعودته.

### المرحلة 7 — التحصين والإطلاق
- القوالب، الواجهة البرمجية الداخلية، لوحة صحة المزامنة، اختبارات الحمل (10 ملفات × 7 أوراق × 500 صف)، النسخ الاحتياطي، دليل استخدام عربي مختصر.

## 16. سيناريوهات اختبار إلزامية (للمزامنة)

1. إنشاء 50 صفاً دفعة واحدة باللصق ← 50 مهمة بلا تكرار، مع احترام حدود المعدل.
2. فرز الورقة بعمود التاريخ ← لا تتغير هوية أي مهمة (الاعتماد على `__uid`).
3. حذف صف ثم التراجع (Ctrl+Z) فوراً ← المهمة تُستعاد من السلة لا تُنشأ من جديد.
4. نقل مهمة في Basecamp إلى قائمة أخرى ← ينتقل الصف بين الأوراق مع مهامه الفرعية.
5. إزالة عضو من مشروع Basecamp ← تنبيه على خلاياه دون فقد للبيانات.
6. انتهاء صلاحية رمز Basecamp ← تجديد تلقائي، وإن فشل: تنبيه لـ `admin` وتعليق المزامنة بأمان دون فقد التعديلات المحلية.
7. ورقة محلية فيها معادلات تقرأ من ورقة متزامنة ← تتحدّث القيم عند وصول تعديل وارد.
8. تعديل عمود حر مضبوط على «إلحاق بالوصف» ← يُحدَّث القسم المخصص في الوصف دون المساس ببقية الوصف أو المرفقات.
9. تعديل تاريخ مهمة رئيسية فقط ← يصل Basecamp **ومسؤولوها ووصفها كما هم** (اختبار مباشر لخطر مسح الحقول في `PUT`).
10. حذف مهمة فرعية ← حوار التحذير من الحذف النهائي يظهر، ونسختها محفوظة في السجل، والتراجع يعيد إنشاءها.
11. مستخدمان يعدّلان صفين في الورقة نفسها ← يظهر في Basecamp كل تعديل باسم صاحبه.
12. مستخدم لم يربط حسابه في Basecamp ← لا يستطيع تحرير ورقة متزامنة، ويرى زر الربط.
13. مهمة رئيسية بلا مسؤول لها 3 فرعيات مسندة لـ (أ)، (ب)، (أ) ← تُسند الرئيسية لـ (أ) و(ب) في الورقة وBasecamp، دون إشعار مكرر.
14. إسناد فرعية جديدة لـ (ج) من داخل Basecamp ← تُضاف (ج) للرئيسية تلقائياً خلال المهلة المحددة.
15. إسناد الرئيسية يدوياً لـ (د) ثم تغيير مسؤولي الفرعيات ← الرئيسية تبقى (د) فقط. إفراغها ← تعود للاتحاد فوراً.
16. التحديث التلقائي يعود كـ Webhook ← لا حلقة تحديثات ولا تحوّل للوضع اليدوي.
17. إسناد مهمة لعضو في الحساب خارج المشروع ← حوار الإضافة، ثم يصبح عضواً في المشروع ومسنداً في Basecamp.
18. مستخدم بلا صلاحية إدارة الأشخاص يحاول الحالة 1 ← رسالة واضحة، وطلب يصل لـ `admin`، والصف «بانتظار إضافة عضو».
19. دعوة عضو فريق جديد والحساب بلغ حد المستخدمين (`507`) ← رسالة واضحة واقتراح الجهة الخارجية، ولا يُنشأ شيء جزئياً.
20. مهمة مسندة لاثنين من Basecamp وجهة خارجية ← الاثنان في `assignee_ids`، والخارجي في الكتلة المُدارة، وما كتبه الناس في الوصف لم يتغير.
21. مهمة مسندة لجهة خارجية فقط ← لا يُحفظ الإسناد قبل تحديد متابع داخلي؛ المتابع مسند في Basecamp.
22. مهمة فرعية لجهة خارجية فقط ← المتابع مسند للفرعية في Basecamp، والخارجي ظاهر في المنصة فقط.
23. إسناد جهة خارجية مع تفعيل البريد ← يصلها بريد بلا أي رابط للمنصة؛ وتذكير قبل الموعد بيومين.
24. تعديل الكتلة المُدارة يدوياً في Basecamp ← تُعاد كتابتها من المنصة ويُسجَّل ذلك.

## الملحق (أ) — مرجع Basecamp API المُتحقَّق منه

> المصدر: الوثائق الرسمية `github.com/basecamp/bc-api` (فرع master، نوفمبر 2026). هذا المرجع معتمَد للتنفيذ؛ إن ظهر تعارض أثناء الاختبار الحي فأبلغ ولا تخمّن.

### أ-1. أساسيات
- **العنوان الأساسي:** `https://3.basecampapi.com/{account_id}/` — HTTPS فقط، بلا بادئة `/api/v1`.
- **المسارات المسطّحة (Flat routes)** هي الشكل المعتمد: الوصول لأي عنصر بمعرّفه دون معرّف المشروع (مثل `/todos/{id}.json`). الاستثناء: إنشاء الـ Webhooks وعرضها يتطلبان الشكل `/buckets/{project_id}/...`.
- **المصادقة:** OAuth 2.0 فقط (Launchpad)، والرمز في `Authorization: Bearer`.
- **`User-Agent`** إلزامي باسم التطبيق ووسيلة تواصل، و**`Content-Type: application/json`** إلزامي في الإرسال.
- **الترقيم:** ترويسة `Link` (rel="next")، و`X-Total-Count` للعدد الكلي.
- **التخزين المؤقت:** خزّن `ETag`/`Last-Modified` وأعدها في `If-None-Match`/`If-Modified-Since`؛ `304` = لا تغيير.
- **الأخطاء:** `429` + `Retry-After`؛ `5xx` إعادة بتراجع أسّي؛ `404` لا يُعاد (وقد يحمل `Reason: Account Inactive`).
- **الحالة ≠ الإنجاز:** `status` (active/archived/trashed) حالة نشر، و`completed` إنجاز. المهمة قد تكون منجزة ونشطة معاً.

### أ-2. هيكل المهام
```
Project (= bucket، نفس المعرّف)
 └── dock → todoset (واحد لكل مشروع، تأكد أن enabled: true)
      └── Todolist  (= ورقة)
           └── Todo (= صف رئيسي)
                └── Subtask (type: "Kanban::Step") (= صف فرعي، مستوى واحد)
```
- أعضاء المشروع (للقائمة المنسدلة): `GET /projects/{project_id}/people.json`.
- المستخدم الحالي (لربط الحساب): `GET /my/profile.json`.
- `personable_type` مجموعة مفتوحة (User, Agent, Integration, Tombstone…)؛ لا تفشل عند قيمة جديدة. اعرض في القائمة المنسدلة الأشخاص من نوع `User` (ويشمل `client: true` إن رغبتم — **قرار تشغيلي**).

### أ-3. القوائم (Todolists)
| العملية | المسار |
|---|---|
| قوائم المشروع | `GET /todosets/{todoset_id}/todolists.json` |
| إنشاء قائمة | `POST /todosets/{todoset_id}/todolists.json` |

### أ-4. المهام (To-dos)
| العملية | المسار | ملاحظات |
|---|---|---|
| مهام قائمة | `GET /todolists/{id}/todos.json` | افتراضياً النشطة غير المنجزة فقط؛ `?completed=true` للمنجزة؛ `?status=archived\|trashed` |
| مهمة واحدة | `GET /todos/{id}.json` | فيها `subtasks_count`, `subtasks_completed_count`, `subtasks_url`, و`steps` (أول 100 فرعية، قراءة فقط) |
| إنشاء | `POST /todolists/{id}/todos.json` | `content` إلزامي؛ اختياري: `description` (HTML)، `assignee_ids[]`، `completion_subscriber_ids[]`، `notify`، `due_on`، `starts_on` |
| تحديث | `PUT /todos/{id}.json` | ⚠ **أرسل كل الحقول**؛ الحقل المحذوف من الطلب يُمسح |
| إنجاز / إلغاء | `POST` / `DELETE /todos/{id}/completion.json` | `204` |
| إعادة ترتيب / نقل | `PUT /todos/{id}/position.json` | `position` ≥ 1؛ `parent_id` اختياري للنقل لقائمة أخرى في المشروع نفسه (وإلا `422`) |
| سلة المهملات | عبر نقطة Recordings (trash a recording) | قابل للاسترجاع |

### أ-5. المهام الفرعية (Subtasks)
| العملية | المسار | ملاحظات |
|---|---|---|
| فرعيات مهمة | `GET /recordings/{todo_id}/subtasks.json` | مقسّمة صفحات، مرتبة حسب الموضع |
| فرعية واحدة | `GET /subtasks/{id}.json` | |
| إنشاء | `POST /recordings/{todo_id}/subtasks.json` | `title` إلزامي؛ اختياري: `due_on`، `assignee_ids[]`؛ يُرجع `201` |
| تحديث | `PUT /subtasks/{id}.json` | **جزئي**؛ `"due_on": null` يمسح التاريخ، `"assignee_ids": []` يزيل المسؤولين |
| إنجاز / إلغاء | `POST` / `DELETE /subtasks/{id}/completion.json` | `204` |
| إعادة ترتيب | `PUT /subtasks/{id}/position.json` | `position` يبدأ من **1** |
| حذف | `DELETE /subtasks/{id}.json` | ⚠ **نهائي**؛ `403` إن كان الحذف مقصوراً على المدراء والمنشئ |

**حقول الفرعية المتاحة فقط:** `title`, `due_on`, `assignees`, `completed`, `position`, `parent`. **لا يوجد:** وصف، تاريخ بدء، مرفقات، تعليقات.

### أ-6. الـ Webhooks
| العملية | المسار |
|---|---|
| إنشاء | `POST /buckets/{project_id}/webhooks.json` — `payload_url` (HTTPS) + `types[]` |
| عرض الكل | `GET /buckets/{project_id}/webhooks.json` |
| عرض واحد (مع آخر 25 تسليماً للتشخيص) | `GET /webhooks/{id}.json` |
| تحديث / إعادة تفعيل | `PUT /webhooks/{id}.json` — `payload_url`, `types`, `active` |
| حذف | `DELETE /webhooks/{id}.json` |

- **الأنواع المستخدمة:** `Todo`, `Todolist`, `Kanban::Step`, `Comment`, `Upload`.
- **شكل الحمولة:** `{ id, kind, details, created_at, recording{ id, type, parent, bucket, title, content, ... }, creator }` — **بدون** `description`/`completed`/`assignees`.
- **إعادة المحاولة:** حتى 10 مرات بتراجع أسّي ثم تعطيل؛ النجاح = `2xx` فقط؛ لا يتبع `3xx`.
- **الحد:** `507` عند بلوغ حد الـ Webhooks في الحساب — نبّه `admin`.
- العملاء (client users) لا يستطيعون إدارة الـ Webhooks (`403`)؛ استخدم رمز الخدمة.

### أ-7. إدارة الأشخاص في المشروع
| العملية | المسار | ملاحظات |
|---|---|---|
| منح/سحب الوصول لمشروع | `PUT /projects/{id}/people/users.json` | `grant[]` لأعضاء الحساب، `revoke[]`، و`create[]` (`name`, `email_address`, اختياري `title`, `company_name`) لشخص جديد |
| تسجيل أشخاص في الحساب | `POST /account/enrollments/people.json` | يتطلب صلاحية إدارة الأشخاص؛ `people[]`، `project_ids[]`، `notify`؛ `507` عند بلوغ حد المستخدمين؛ العملية كلها أو لا شيء |
| تفعيل العملاء في مشروع | `POST /projects/{id}/client_enablement.json` | ⚠ يغيّر ظهور أدوات المشروع للعملاء افتراضياً |
| إضافة/إزالة عملاء | `PUT /projects/{id}/people/client_users.json` | يتطلب تفعيل العملاء أولاً (وإلا `403`) |
| كل أشخاص الحساب | `GET /people.json` | البريد مُخفى إلا للمدراء والمالكين — **لذا مطابقة `naf-id` بالبريد تتم برمز الخدمة (مدير)** |
